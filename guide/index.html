Why the order of rows matters

SpMV reads x[j] for every nonzero. Where that value comes from decides how fast the kernel runs, and the ordering decides where it comes from.

Step 1 · Memory is a ladder

Each value is served by the closest level that holds it. Every dot below makes round trips at the speed of its level, and the counter shows how many values it delivered:

Measured on the cluster node that ran SparseViz (AMD EPYC 7601) with a small pointer-chasing test: one core follows a random chain of pointers through 16 KiB, 256 KiB, 4 MiB and 1 GiB of memory, so every load has to wait for the one before. Played 40 million times slower. In the time RAM returns one value, L1 returns about 100. A kernel that keeps finding its data in cache runs many times faster than one that keeps going to RAM.

The cache is a toy model computed in your browser: cache lines of 8 doubles, room for 16 lines, least-recently-used eviction. Real caches are bigger, so the gap shows up on bigger matrices: on NACA0015 (1 million rows) SparseViz measured MySpMV at 31.7 ms in natural order and 9.6 ms after RCM on one thread (details below).

  







  

    
Why SparseViz times both the ordering and the kernel

    
An ordering costs time once, up front: computing the order and building the reordered matrix. It pays off only if the faster kernel runs often enough to win that time back. The presets are SparseViz's real numbers for NACA0015 (1 million rows, 6.2 million nonzeros), MySpMV on one thread; move the sliders to try your own.

An iterative solver such as CG calls SpMV once per iteration, often hundreds or thousands of times. SparseViz gives you all the numbers: the ordering time in the CSV's Matrix Ordering block, the time to build the reordered matrix in the log (Constructing a RCM ordered …), and the kernel time for every ordering. With RCM on NACA0015, 0.33 s of ordering plus 0.69 s to build the reordered matrix is won back after about 47 SpMV calls; PaToH's 10.0 s + 0.69 s needs about 628.

MySpMV, average of 17 timed runs per point (N_RUN 20, N_IGNORE 3), on a whole defq node (AMD EPYC 7601, 64 cores in 8 NUMA domains). Thread counts follow the NUMA layout: 1, 2, 4, 8 inside one domain, then whole domains.

    

      
      

      
Solid lines: the first run. Dashed lines: the same config again, started right after. Times come from results.csv of the two runs. Up to 4 threads the runs agree within 8% (the largest gap is DegreeSort at 2 threads: 19.3 vs 20.7 ms). From 8 threads on they can differ a lot: RCM at 64 threads took 2.9 ms in the first run and 5.4 ms in the second. So trust the small thread counts, and repeat a run before you believe a difference at high thread counts. Part of the reason is where the matrix lands in memory; see below. The runs used a temporary build that fixes how dev builds the reordered matrix (see the note below); with dev as it is, every ordering except Natural is timed on a scrambled matrix.

Where the numbers on this page come from
Every matrix picture, ordering, statistic, time and terminal line on this page is real: SparseViz output or a measurement on the cluster. The runs used dev 503e332 with these local changes: the build fixes from the install steps (library paths in CMakeLists.txt, extern "C" in amd.h); the two example classes from this guide, DegreeSort and MySpMV (dev's SPMVRowBased never fills x, so every timing chart on this page uses MySpMV); the extended MatrixVisualizer (all metrics in the metrics section); and a fix for SparseMatrix::generateOrderedMatrix, which on dev builds a wrong reordered matrix for the kernels. One known dev bug was not fixed: SparseMatrix::deepCopy copies the value array with the size of an index (4 bytes) instead of a double (8 bytes), so only the first half of the values is copied and the rest is left uninitialised in the reordered matrices. Their pattern, which decides the memory access, is right; whether the wrong values change the timings was not measured. The cache model above and the small CSR and permutation examples are explanations, not measurements. The latency ladder comes from a small separate test program on the same node, and the per-call and per-thread times from the same build with a trace switch added (off by default).

        02 · Configure
        
    Write a config file
    
        
    The config file tells SparseViz which matrices to load, which orderings and kernels to run, and where to put the results.
    

        
    Syntax rules
    
        
      
          
    • The file is split into sections. Each header sits alone on its line between asterisks: *SETTINGS*, *MATRICES*, *MATRIX_ORDERINGS*, *MATRIX_KERNELS*. The reader also knows *TENSORS*, *TENSOR_ORDERINGS*, *TENSOR_KERNELS*, *GPU_MATRIX_KERNELS* and *GPU_TENSOR_KERNELS*. Put *SETTINGS* first: ZOO_TYPE and MATRIX_FILES_DIR must already be set when the matrix lines are read, and PROJECT_DIR must come before LOGO_PATH.
      • 
          
    • Anything after // is a comment. Leave a space before a comment at the end of a line: ZOO_TYPE = MAT // note.
      • 
          
    • Empty lines must be really empty. A line with only spaces or tabs, a comment that doesn't start in the first column (  // note), or a blank line in a file saved with Windows line endings makes SparseViz crash with a segmentation fault and no message. Start comment lines with // in column 1 and save the file with Unix line endings.
      • 
          
    • SparseViz removes every space in a line. Don't use spaces in folder paths or ordering names. A | B and A|B are the same.
      • 
          
    • Folder settings must end with /. Paths are glued together as is: MATRIX_FILES_DIR + nos4.mtx. Without the slash every matrix is skipped silently and the run produces nothing.
      • 
          
    • One matrix, ordering or kernel per line.
      • 
        
    
        
    Here is what the reader does to every line, step by step:
    
        
    
          
    1 · raw line2 · drop comment3 · drop spaces4 · split

    Matrices (*MATRICES*)

    How RCM works
    
        
    RCM is a breadth-first search with one twist at the end. Here is the order SparseViz's RCM produced for delaunay_n10, replayed row by row:
    
        
    
          
    1 · pick a start2 · number level by level3 · reverse
    
          
    
            
            
          
    
          
    
        
    

        
    What Patoh's first parameter does
    
        
    In Patoh | Patoh8 | 8/CN/UNIT/CUT/END/NONE the first number is how many parts the matrix is split into. Each part becomes a block on the diagonal. Nonzeros that connect two parts fall outside the blocks; PaToH tries to keep that cut small. Pick a part count:
    
        
    
          
    parts
            
    
              
              
            
    
          
    
          
    
            
            
          
    
          
    
            
    parts
    –
    
            
    cut (run log)
    –
    
            
    time to order
    –

    –
    
          
    
          
    These are four orderings from one real SparseViz run (Patoh2, Patoh4, Patoh8, Patoh16, inner order NONE). More parts give smaller blocks that fit in cache more easily, but the cut grows: 66, 126, 235, 346 nets cross part boundaries. Each number is the PaToH cut is … line SparseViz printed. The last parameter (NONE here, RCM in the config example) orders the rows inside each part.
    
          
    Not repeatable run to run: SparseViz seeds PaToH with the clock (args.seed = tp.tv_sec;, line 89 of PatohOrdering.cpp), so computing the same PaToH ordering again can give a different partition and cut. The saved ordering in orderings/ is what makes later runs use the same one.

        05 · Extend
        
    Add your own ordering
    
        
    An ordering is a class that derives from MatrixOrdering and fills in one function. As an example we add DegreeSort, which sorts rows by their nonzero count. This code was built and run on dev.
    

        
    The one thing to know first: which way the permutation points
    
        
    An ordering fills two arrays, rowIPermutation and colIPermutation. The rule: rowIPermutation[old row] = new row. The index is where the row is now; the value is where it goes.
    
        
    
          
    
          
    
            
    before the ordering
    
            
    
            
    Watch each row travel to the slot its array entry names. Row 0 goes to position 2, row 1 to the top. Every new position is used exactly once.
    
          
    
        
    

        
      
          
    1.

#include <numeric>

DegreeSortOrdering::DegreeSortOrdering(SparseMatrix& matrix, std::string orderingName, std::string orderingParameters)
:   MatrixOrdering(matrix, orderingName, true, true, 1),
    m_Descending(true)
{
    // parameters come from the config line, split with '/'
    std::vector<std::string> parameters = split(orderingParameters, '/');
    if (!parameters.empty() && parameters[0] == "ASC")
    {
        m_Descending = false;
    }
}

void DegreeSortOrdering::orderingFunction()
{
    const SparseMatrix& A = this->getMatrix();
    vType n = A.getRowCount();
    vType m = A.getColCount();
    vType* ptrs = A.getPtr();

    // rows: sort by number of nonzeros
    std::vector<vType> rows(n);
    std::iota(rows.begin(), rows.end(), 0);
    std::stable_sort(rows.begin(), rows.end(), [&](vType a, vType b)
    {
        vType degA = ptrs[a + 1] - ptrs[a];
        vType degB = ptrs[b + 1] - ptrs[b];
        return m_Descending ? degA > degB : degA < degB;
    });

    // rowIPermutation[old row] = new row
    rowIPermutation = new vType[n];
    for (vType newPos = 0; newPos < n; ++newPos)
    {
        rowIPermutation[rows[newPos]] = newPos;
    }

    // columns: keep them where they are
    colIPermutation = new vType[m];
    for (vType j = 0; j < m; ++j)
    {
        colIPermutation[j] = j;
    }
}
      
            
      The values passed to the base class constructor:
      
            
      
              
      
                
      ParameterHereMeaning
      
                
                  
      rectangularSupporttrueCan the ordering handle rectangular matrices? Only recorded (the CSV's Ordering Rectangular Support column); the code never acts on it.
      
                  
      patternUnsymmetricSupporttrueCan it handle matrices whose pattern isn't symmetric? With false, any matrix whose pattern isn't symmetric (every rectangular one too) is replaced by a square, pattern-symmetric copy built from A and Aᵀ, without the diagonal and without values (getValues() is null). The result is mapped back to the original rows and columns.
      
                  
      orderingFunctionPrice10–10, how expensive the algorithm is. Expensive orderings start first. It doesn't change results, only shortens the total time.
      
                      
              
      
            
      
            
        
              
      • Get the matrix with this->getMatrix(); the CSR arrays are getPtr(), getInd(), getValues().
        • 
              
      • Allocate both arrays with new but don't free them; the base class does.
        • 
              
      • Always fill both arrays. If you don't touch columns, write colIPermutation[j] = j.
        • 
              
      • SparseViz only checks that every value is in range. A value used twice is not caught (the duplicate check in MatrixOrdering.cpp, lines 178–184, can never fail), so test your arrays yourself; an invalid permutation gives a wrong report without any error.

        05 · Extend
        
    Add your own kernel
    
        
    A kernel is a class that derives from MatrixKernelFunction and fills in three functions. The base class handles timing, thread counts and repetitions. As an example we write MySpMV, an SpMV that follows the schedule from the config. This code was also built and run on dev.
    

        
    The matrix your kernel gets
    
        
    Your kernel receives the reordered matrix in CSR form: getPtr(), getInd() and getValues(). Row i owns the entries from ptr[i] up to ptr[i+1]. This is exactly the loop SpMV runs:
    
        
    
          
    
          
    
          
    
        
    

        
    When each function is called
    
        
    
          
    init(A)once per reordered matrix; return false to skip it
    
          
    
            
    for each thread count in the config (e.g. 1, 2, 4, 8):
    
            
    
              
    N_RUN times:
    
              
    preprocess(A)not timed
    
              
    functionBody(A, r)this is what gets timed
    
            
    
            
    → the average of the last N_RUN − N_IGNORE timings is recorded
    
          
    
          
    ~MySpMV()free your memory here
    
        
    

        
      
          
    1. 
            
      Header
      
            
      #ifndef SPARSEVIZ_MYSPMV_H
#define SPARSEVIZ_MYSPMV_H

#include "MatrixKernelFunction.h"


class MySpMV: public MatrixKernelFunction
{
public:
    MySpMV(const std::string& kernelName, const std::vector<int>& threadCounts, const std::string& schedulingPolicy, int chunkSize, int nRun, int nIgnore)
    :   MatrixKernelFunction(kernelName, threadCounts, schedulingPolicy, chunkSize, nRun, nIgnore), x(nullptr), y(nullptr) {}

    virtual ~MySpMV() override;
    virtual bool init(const SparseMatrix& A) override;
    virtual void preprocess(const SparseMatrix& A) override;
    virtual void functionBody(const SparseMatrix& A, int iterNumber) override;

private:
    vType m, n;
    vType* ptrs;
    vType* ids;
    valType* vals;
    valType* x;
    valType* y;
};


#endif //SPARSEVIZ_MYSPMV_H
      
          
      2. 

          
    2. 
            
      Source file
      
            
      #include "MySpMV.h"
#include "omp.h"


bool MySpMV::init(const SparseMatrix& A)
{
    // called once per ordered matrix, before any run
    m = A.getRowCount();
    n = A.getColCount();
    ptrs = A.getPtr();
    ids = A.getInd();
    vals = A.getValues();

    delete[] x;
    delete[] y;
    x = new valType[n];
    y = new valType[m];
    return true;    // return false to skip this matrix
}

void MySpMV::preprocess(const SparseMatrix& A)
{
    // called before every run, not timed
    for (vType j = 0; j < n; ++j) x[j] = 1.0;
}

void MySpMV::functionBody(const SparseMatrix& A, int iterNumber)
{
    // this is the timed part
    // schedule(runtime) uses the policy and chunk size from the config line
#pragma omp parallel for schedule(runtime)
    for (vType i = 0; i < m; ++i)
    {
        valType sum = 0;
        for (vType p = ptrs[i]; p < ptrs[i + 1]; ++p)
        {
            sum += vals[p] * x[ids[p]];
        }
        y[i] = sum;
    }
}

MySpMV::~MySpMV()
{
    delete[] x;
    delete[] y;
}
      
            
        
              
      • The same kernel object is reused for every matrix, which is why init frees the old arrays before allocating new ones.
        • 
              
      • Without schedule(runtime), the schedule and chunk from the config are ignored and OpenMP's default is used. The built-in SPMVRowBased doesn't use them.
        • 
              
      • Don't set the thread count yourself. The base class calls omp_set_num_threads once for each thread count in the config line, before that count's N_RUN runs, and resets it afterwards.

        05 · Extend
        
    Tensors and GPU kernels
    
        
    Adding a tensor ordering (TensorOrdering) or tensor kernel (TensorKernelFunction) works the same way, with one difference: a tensor ordering's constructor takes (SparseTensor&, const std::vector<vType>& active_modes, std::string name, …), and it fills orderedDimensions instead of two permutation arrays. Files go under include/Tensor/Orderings and include/Kernel/Tensor/CPU. The factories are tensorOrderingFactory (built in: Natural, KPartite) and tensorKernelFactory (built in: COOTensorKernel, only with TENSOR_STORAGE_TYPE = COO).
    
        
    In the config, use ZOO_TYPE = TENS, TENSORD or FULLTENSOR, set the three tensor folders (see Settings), and list tensors under *TENSORS* as name.tns or name.tns | 0/1/2 (three different modes). Tensors are read from disk, never downloaded. Tensor kernel lines take an optional seventh field for parameters. We did not run tensors for this page.
    
        
    GPU kernels need a CUDA build. Their lines go under *GPU_MATRIX_KERNELS* or *GPU_TENSOR_KERNELS* and have eight fields:
    
        
    Class | Name | grid sizes | block sizes | shared memory | parameters | N_RUN | N_IGNORE
    
        
    On dev, matrixGPUKernelFactory returns nothing for every name, so each GPU matrix line prints SKIPPING MATRIX GPU KERNEL: … until you add a branch for your own MatrixGPUKernel class (with init, preprocess and hostFunction). In tensorGPUKernelFactory the two built-in names are swapped: COOTensorGPUKernelSoA builds the AoS class and the other way round. Without CUDA these sections only print WARNING: CUDA SUPPORT COULD NOT BE FOUND! …. We did not build or run the GPU part for this page.
    
        
    For details see the repository's docs/ folder or the official documentation. Some config examples there use an older format; the formats on this page were checked against the code.
    
      
    

      
      
    
        06 · Help
        
    Troubleshooting
    
        
    Messages are written as the program or the build prints them (long ones shortened with …), so you can search for the line you see in your terminal.
    
        
    
          
    
            file failed to open for reading … /home/user/sparseviz/deniz_matrix.config
            
    The hardcoded paths in CMakeLists.txt are still there. Do step 4 of the build.
    
          
    
          
    
            undefined reference to `amd_order(int, int const*, …)'
            
    amd.h is missing extern "C". See build step 5.
    
          
    
          
    
            No rule to make target '…/lib/libamd.a', needed by 'SparseViz' or undefined reference to `SuiteSparse_malloc'
            
    The first means the file isn't in lib/. The second means libsuitesparseconfig.a is missing from lib/ or from CMakeLists.txt. See steps 3 and 4.
    
          
    
          
    
            AMD is failed on <matrix> and the run stops
            
    
              
    A known issue on dev. SparseViz stores every entry of a symmetric .mtx file twice, the diagonal too, so each diagonal entry appears twice in its row. AMD reports duplicate entries as AMD_OK_BUT_JUMBLED. That's a valid result, but the code only accepts AMD_OK. It happened on both symmetric matrices we tried (nos4, can_1072); both have a full diagonal. For now, remove AMD from your config.
    
              
    ~/SparseViz · real output, WMO/RMO lines left out
    
              
    To fix it in your own copy, widen the check in src/Matrix/Orderings/AMDOrdering.cpp. The amd.h in the repository is older and has no name for this status, so compare with its value, 1:
    
              
    -    if(status == AMD_OK)
+    if(status == AMD_OK || status == 1)   // 1 = AMD_OK_BUT_JUMBLED
    
              
    With this change AMD finished on nos4 and can_1072 in our test build.
    
            
    
          
    
          
    
            A run was interrupted, and the next one fails with std::bad_alloc or a segfault
            
    
              
    When a run crashes or is stopped, some cache files are left empty (0 bytes). The next run reads them, gets a broken ordering and fails during the kernels. Delete the empty files and run again:
    
              
    find orderings matrices -size 0 -print -delete
    
              
    ~/SparseViz · real output, shortened
    
            
    
          
    
          
    
            A matrix is missing from the results
            
    Matrices are dropped without any message in two cases: SuiteSparse doesn't know the name (it must match exactly: nos4.mtx, bcsstk17.mtx), or MATRIX_FILES_DIR doesn't end with / (the folder is glued to the file name, so …/matrices + nos4.mtx is looked up as matricesnos4). Matrix download for matrix: … has failed. appears only when SuiteSparse knows the name but the download or unpacking fails. For your own matrices, see the warning in Matrices.
    
          
    
          
    
            SKIPPING ORDERING: … or SKIPPING KERNEL: …
            
    The class name in the config isn't in the factory. Check the spelling (case matters). If it's your own class, make sure you added the factory branch and rebuilt.
    
          
    
          
    
            Invalid format for CHUNK_SIZE of … (or N_RUN, N_IGNORE)
            
    The fourth, fifth or sixth field isn't a number. Usually the line comes from the older docs, which have an extra name field (Class | Name | threads | …), so the schedule lands in the chunk field. Correct: SPMVRowBased | 1/2/4/8 | static | 0 | 10 | 2. A line with fewer than six fields is not caught: it reads past the end of the line and may run with random values or crash.
    
          
    
          
    
            YOU MUST SET … SETTING EXPLICITLY IN THE CONFIG FILE! or MAT AND MATORD ZOO TYPES REQUIRE YOU TO INDICATE FOLLOWING SETTINGS EXPLICITLY: …
            
    A required setting is missing: PROJECT_DIR, ZOO_TYPE or CHART_TYPE (first message), or one of the three folder settings (second message). YOU HAVE INDICATED INCORRECT … means the value isn't one of those listed in the message. Check the spelling and that the line sits under *SETTINGS*.
    
          
    
          
    
            Failed to open the file: …
            
    The .mtx file is in MATRIX_FILES_DIR but couldn't be opened, for example because you have no read permission for it (check with ls -l matrices/). A missing / at the end of MATRIX_FILES_DIR doesn't cause this message; it makes the matrices disappear without one (see “A matrix is missing from the results”).
    
          
    
          
    
            Segmentation fault right after the start, before any output
            
    Usually a line in the config that looks empty but isn't: spaces or tabs, an indented // comment, or Windows line endings (check with cat -A myconfig; a ^M at the end of a line shows them). See Syntax rules.
    
          
    
          
    
            …/orderings/…: Cannot open the output file!
            
    The folder in MATRIX_ORDERING_FILES_DIR doesn't exist. SparseViz doesn't create it; run mkdir -p orderings html.
    
          
    
          
    
            The run finishes but html/ has no report
            
    The folder in MATRIX_VISUALIZATION_FILES_DIR doesn't exist. SparseViz writes nothing there and prints no error. Create the folder and run again; orderings and reordered matrices come from the cache.
    
          
    
          
    
            curl_easy_perform failed: …
            
    The node can't reach sparse.tamu.edu. Every run downloads the SuiteSparse index first, even when all matrices are already on disk, so it needs internet. A web server error shows up as HTTP … for URL: … instead. On a cluster, try a node or partition with internet access.
    
          
    
          
    
            I changed a parameter but the result didn't change
            
    Two caches are read: the ordering (orderings/<Name>_<matrix>.bin) and the reordered matrix the kernels run on (matrices/<Name>_ordered_<matrix>.mtx.bin). Give the ordering a new name, or set both USE_EXISTING_ORDERINGS = FALSE and USE_EXISTING_ORDERED_SPARSE_STRUCTURES = FALSE. With only the first, the ordering is computed again, but the kernels still run on the old reordered matrix.
    
          
    
          
    
            dynamic and static give the same times
            
    Two reasons. On dev, dynamic and guided are currently mapped to static. And if the kernel's loop has no schedule(runtime), the setting isn't used at all.
